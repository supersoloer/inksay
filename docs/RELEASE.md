# 开源发布与发行检查

## 当前准备范围

当前准备的是首个 GPL-3.0-only 桌面源码发布，iOS 不在本次公开范围内。尚未创建公开远程仓库、公开 Tag 或 GitHub Release。macOS 公证、Windows 代码签名不属于已经完成的事项。

## 首次公开源码

本地仓库保留完整开发历史和内部研究资料。`ios/` 已从当前 Git 索引移除并加入忽略，但过去的本地提交仍含 iOS。`.gitattributes` 的 `export-ignore` 只影响源码归档，不会清除 Git 历史，也不会让这些文件在普通 Git push 时消失。

首次公开建议使用经过审查的源码归档初始化新的公开仓库，保留本地完整历史用于开发追溯。不要直接执行 `git push --mirror`。

```sh
npm run check:public
# 审查并提交准备工作后
npm run package:source
```

导出包位于 `build/releases/source/`，旁边的 manifest 记录来源 commit、版本、许可证和 SHA-256。包不包含 `ios/`、`.git`、内部竞品调研、旧迁移资料、构建产物、个人档案或旧项目恢复包。源码内的程序、测试、提示词和构建脚本保持完整。

解压后检查文件与清单，按[开发指南](DEVELOPMENT.md)初始化新 Git 仓库，设置你选择的远程地址，再由维护者明确执行公开推送。公开仓库的初始 commit 会与本地来源 commit 不同。

## 每次发布前

- [ ] 版本在 package.json、package-lock.json、Cargo.toml、Cargo.lock 和 Tauri 配置中一致。
- [ ] 更新 CHANGELOG，说明各平台实际验收范围，不把编译检查标记为运行成功。
- [ ] 运行公开文件检查，人工复查 Git 历史、图片、音频、许可证与截图。
- [ ] 更新依赖许可清单，核查仅有元数据/README 许可声明的组件；生成器并非法律审查工具。
- [ ] 使用干净源码检出运行构建和相应测试，不依赖个人配置、证书或已有 sidecar。
- [ ] 用实际应用截图展示功能，隐藏个人历史、窗口内容、密钥及私有服务地址。
- [ ] 发行二进制、源码、第三方源码与说明对应同一版本；原始来源与公开 commit 的关系应有记录。

## GPL 对应源码

项目源码归档用于公开本项目。分发二进制时，还要提供该发行所需的完整对应源码：

- InkSay 前后端、提示词、修改、构建及打包脚本。
- 编入发行的 Rust 与前端依赖的固定版本源码和许可通知，可使用 `cargo vendor --locked` 及保留的 npm 包来源准备；不能只放一份 SPDX 清单。
- 固定 revision 的 whisper.cpp / ggml 源码、实际应用的补丁及构建配置。
- 必要的资源、接口定义及安装信息。不得把 API Key、个人证书或维护者账号作为构建前提。

一般可用的未修改编译器、操作系统库和工具可单独按其条款获取。不要把“普通源码包”“完整对应源码包”和“应用安装包”混为一个产物。

首次仅公开本项目源码时不必发布尚未准备好对应源码、公证或签名的二进制。若未来采用商店或设备受限的分发方式，需要另外评估许可证、贡献授权及平台条款；当前没有作出兼容保证。

## 二进制质量与信任

### macOS

- 验证主 App、sidecar、资源和音频 entitlement。
- 对外分发使用适当的 Developer ID 签名、公证并装订，另行验收下载后的 Gatekeeper 行为。
- Apple Development 签名、本机启动或 `codesign --verify` 成功都不等同于公证完成。

### Windows

- 在实际 Windows x64 环境确认安装/解压、快捷键、录音、浮窗及目标应用写入。
- 记录系统、架构、测试工具与限制。CI 验证 NSIS 构建，默认不上传或发布该未签名测试产物。
- 准备 Authenticode 签名与发布渠道，校验下载后的行为。

## 发布信息

公开仓库说明应写清楚版本、平台、安装步骤、数据行为、已知限制、源码获取方式和校验信息。不要填写尚未创建的 GitHub 下载链接、未通过的 CI 徽章或并未执行的验收结果。
